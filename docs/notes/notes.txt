1. WHY FIVE MODELS

DataPact tracks five distinct things, and each one has its own lifecycle:

  Dataset         a data asset a team registers once
  Contract        an agreed-upon schema for that dataset, at a point in time
  ValidationRule  a single assertion about a single column
  ValidationRun   one uploaded file checked against one contract
  Violation       the result when one rule fails during one run

Collapsing any two of these loses information. Rules cannot live on Dataset
because different contract versions have different rules. Violations cannot
live on ValidationRule because the same rule can fail in many runs. Runs
cannot live on Dataset because a run is only meaningful relative to the
contract it was judged against.

Django's built-in auth.User is used for ownership and submission rather than
writing a sixth model, so authentication and the admin site work without
extra code.


2. WHY CONTRACT IS ITSELF A VERSION

A common alternative is Contract + ContractVersion, where Contract is a
container and ContractVersion holds the actual columns and rules. We rejected
that because the container would carry no data of its own - every meaningful
field (status, rules, change note) would sit on the version, leaving Contract
as an empty parent row.

Instead, Contract carries version_number directly. Changing a contract means
inserting a new Contract row for the same dataset with the next version
number. This keeps one join shorter on every query and makes the version
history a simple ordered list of Contract rows filtered by dataset.


3. WHY VALIDATIONRUN HAS NO DATASET FOREIGN KEY

ValidationRun stores contract only. The dataset is reached by
run.contract.dataset.

Storing dataset directly on ValidationRun would create two independent paths
to the same fact. Nothing in the schema would stop a row where
run.dataset_id = 4 and run.contract.dataset_id = 7. That row would be
silently wrong, and every report built on it would be wrong in a way that is
hard to detect. One path means the two answers cannot disagree.

The cost is one extra join, which is acceptable at this scale.


4. WHY CONTRACT -> VALIDATIONRUN USES PROTECT

A validation run is an audit record. It states that on a specific date, a
specific file was checked against a specific set of rules and produced a
specific outcome.

If Contract used CASCADE, deleting a contract would silently erase every run
that referenced it, and the audit trail would disappear with no warning.
PROTECT makes the database refuse the delete instead. A user who really wants
to remove a contract has to deal with its history first, deliberately.


5. WHY DATASET.OWNER -> USER USES PROTECT

Ownership is accountability. If a user account is deleted and the datasets
cascade away with it, every contract, run, and violation underneath them
disappears too - a large amount of history removed by one action on an
unrelated table.

PROTECT forces datasets to be reassigned to a new owner before the user can be
removed. Deactivating a user account (is_active = False) remains available and
is the normal path for someone leaving a team.


6. WHY VALIDATIONRUN.SUBMITTED_BY -> USER USES SET_NULL

This is the opposite case. Ownership of a dataset is a live responsibility
that must be reassigned; submitting a file is a past event that is finished.

The run itself stays valid whether or not the submitter still has an account.
SET_NULL lets the user row be removed while keeping the run, its row count,
its status, and its violations intact. The field reads as "submitted by
someone no longer in the system," which is accurate. This requires
null=True on the field.


7. WHY CONTRACT(DATASET, VERSION_NUMBER) IS UNIQUE

Version numbers are only useful if they identify exactly one contract. Without
the constraint, two rows could both claim to be version 3 of the same dataset,
and "which rules was this run judged against?" would have two answers.

The constraint is scoped to dataset, not global, so each dataset counts its
own versions from 1.


8. WHY VIOLATION(RUN, RULE) IS UNIQUE

A Violation is an aggregated result, not one row per failing cell. It records
that rule R failed during run N, how many rows failed, and a small sample of
the offending values.

That is one fact, so it gets one row. The constraint prevents a partially
re-run validation from writing a second Violation for the same rule and
inflating the failure counts. It also keeps the table small: a file with
50,000 bad rows produces one Violation, not 50,000.


9. IMMUTABILITY OF USED CONTRACTS

Once a ValidationRun has referenced a contract, that contract is treated as
immutable. Editing its rules afterwards would change the meaning of a run that
already happened: a run recorded as passing could later appear to have been
judged by rules it never saw. Changes are made by creating a new Contract
version instead.

This is currently a convention, not a constraint. A1 does not enforce it at
the database level - nothing stops an admin from editing the rules of a used
contract. The foreign key structure supports the rule (old runs keep pointing
at the old contract) but does not police it. Enforcement is deferred to
application-level validation in a later assignment.


10. OBSERVED BEHAVIOR WHEN DELETING A USED CONTRACT

Deleting a Contract that has been used by a validation run fails, and it is
worth being precise about why, because two separate mechanisms are involved.

Django first collects everything the delete would touch:

  Contract -> ValidationRule is CASCADE, so the contract's rules are
  collected for deletion.

  ValidationRule -> Violation is PROTECT, so any rule that has produced a
  violation refuses to be deleted, which blocks the cascade.

  Contract -> ValidationRun is PROTECT, so the contract is independently
  protected by its own runs.

The result is a ProtectedError and no rows change. The two protections are not
redundant. The run-level PROTECT stops the delete when a contract has been
used at all. The violation-level PROTECT stops it in the narrower case where
individual rules have recorded results. A contract that has never been used
has no runs and no violations, so it deletes cleanly along with its rules -
which is the intended behavior for a draft.


11. DEMO SUITE RESULTS

The A1 demo suite (run_a1_demos.py) passes 8 of 8 checks.

The destructive checks - attempting to delete a protected user, a used
contract, and a rule with violations - are wrapped in transactions that roll
back after the expected ProtectedError is raised. The database is unchanged
after the suite runs, and the suite can be run repeatedly without reseeding.


12. DATABASE

The project uses SQLite, Django's default backend. The database file is
db.sqlite3 at the project root. No additional database service is required to
run the project.

13. SECTION 2 VIEWS - NAME AND PURPOSE (per view kind)

CBVs (Hriday):

  data_quality.views.DatasetOverviewView
    Kind: Base CBV, inherits django.views.View, implements get().
    URL:  /datasets/overview/  (name: data_quality:dataset-cbv-base)
    Purpose: manually queries Dataset plus its related contracts, and
    computes two things a generic ListView's context would not give for
    free: how many contract versions each dataset has, and which one (if
    any) is currently ACTIVE. This is the "Dataset Overview" screen -
    shows why a hand-written get() earns its place: as soon as a page
    needs a value derived by walking a relationship instead of a bare
    field on the model, ListView's context stops being enough and you
    want the manual control View gives you.

  data_quality.views.DatasetListView
    Kind: Generic CBV, django.views.generic.ListView.
    URL:  /datasets/  (name: data_quality:dataset-list)
    Purpose: the plain dataset registry (wireframe screen 1). model =
    Dataset, context_object_name = "datasets". No custom logic needed
    here, which is exactly when ListView is the right tool - a plain
    "show me all the rows" page.

  data_quality.views.DatasetDetailView
    Kind: Generic CBV, django.views.generic.DetailView.
    URL:  /datasets/<int:pk>/  (name: data_quality:dataset-detail)
    Purpose: one dataset plus its contract version history (wireframe
    screen 2). model = Dataset, context_object_name = "dataset"; adds
    "contracts" to the context via get_context_data() so the template can
    list every version, active and retired, of that dataset's contract.

FBVs (teammate - fill in once written):

  data_quality.views.dataset_manual  (Connor Slattery, cslat)
    Kind: Function-based view, django.http.HttpResponse.
    URL:  /datasets/manual/  (name: data_quality:dataset-manual)
    Purpose: lists the count and name of every Dataset. The HTML is
    built as a string and returned with HttpResponse. No
    template and no render(). Names go through escape() so odd
    characters cannot break the page.

  data_quality.views.dataset_render  (Tejas Jaggi, tejasj2)
    Kind: Function-based view, django.shortcuts.render().
    URL:  /datasets/render/  (name: data_quality:dataset-render)
    Purpose: the same dataset registry as DatasetListView, built the
    "shortcut" way the assignment describes: query the model
    (Dataset.objects.select_related("owner") - the template prints each
    owner's username, so the join avoids one query per row), put the
    queryset in a context dict under the key "datasets", and hand both to
    render(). It deliberately reuses data_quality/dataset_list.html: the
    template does not know whether a generic ListView or a plain function
    supplied "datasets", which is the Section 3 "same template for both
    views" point.

14. BONUS REFLECTION - WHEN EACH KIND WAS ACTUALLY USEFUL

Base CBV vs Generic CBV: the generic ListView and DetailView were the
obvious choice as soon as the page was "show me the queryset" or "show me
one row" with nothing extra attached - writing that by hand in a base View
would just be re-implementing get_queryset()/get_object() for no benefit.
The base View earned its place exactly once the page needed something a
generic view's context does not compute on its own: per-dataset contract
counts and "which contract is active," both of which require walking
dataset.contracts.all() and branching on status. That could technically be
forced into a ListView with a custom get_queryset() and annotations, but
at that point a plain View with an explicit get() was more readable than
fighting the generic view's assumptions.

HttpResponse vs render (Connor): dataset_manual was quick to write
because it needed no template file. Building plain HTML in Python is
fine for a small check page or a simple text answer. It got awkward
fast, though. The HTML sits inside string concatenation, so any layout
change means editing Python, and there is no shared base.html or
styling. For the real screens (registry, detail) a template is the
better choice, which is why those views use render(). Tejas can add
the render() side. 

render() (Tejas): the render() view is three lines that do exactly what
the HttpResponse view does by hand - fetch, pack into a context, return -
without any HTML in Python. What made it worth having as a separate view
kind is that it let the FBV point at the template Hriday already wrote
for the ListView. Nothing in dataset_list.html changed, and the page is
byte-for-byte the same registry; only the way the data arrived differed.
That is the moment "templates independent of how data is passed" stopped
being a slogan: the FBV and the generic CBV share one template, and the
test suite checks they render the same rows. HttpResponse still earns its
place for tiny diagnostic pages where a template file would be overhead.

23. A3 SECTION 6 - API PLAN (Connor)

Endpoint: data_quality.views.dataset_api

Kind: Function-based view, django.http.JsonResponse.

response type.

STATIC FILE ORGANIZATION CHOICE (asked for by the rubric)

App level, not project level: data_quality/static/data_quality/...

  The app owns these files the same way it owns its templates, so they
  travel with it. The app-directories finder is on by default, which
  means no STATICFILES_DIRS entry and one less thing in settings that
  can be wrong.

  The doubled folder name is not a typo. Everything under every app's
  static/ is flattened into one namespace by collectstatic, so a bare
  css/style.css in two apps would collide and one would silently win.
  Nesting under the app name makes the path unique. Same reasoning as
  templates/data_quality/.

  A project-level static/ would have been the alternative. It suits
  assets that belong to the site rather than to one app - a favicon for
  the whole domain, a shared brand kit. We have one app, so that would
  have been a directory in settings for no gain today.

CACHE BUSTING (rubric asks for the explanation; implemented for the bonus)

  The problem: a browser told to cache datapact.css for a year will keep
  serving the old copy after we edit it. Tell it not to cache, and every
  page load re-downloads the file for no reason.

  The fix is to make the filename depend on the contents. In production,
  collectstatic hashes each file and writes a copy under the hashed name:

    datapact.css  ->  datapact.e5ab6567e31e.css

  and records the mapping in staticfiles/staticfiles.json. {% static %}
  reads the manifest, so base.html emits the hashed URL. WhiteNoise then
  serves it with:

    Cache-Control: max-age=315360000, public, immutable

  Ten years, never revalidate. That is safe precisely because the name
  changes: edit the CSS and the hash changes, so the next page asks for a
  URL nothing has cached. Stale CSS stops being possible, and nobody has
  to remember to hard-refresh.

  Development skips all of this. DEBUG = True serves the plain filename
  straight from the app folder, so an edit shows up on reload.

  Full transcript of both modes: docs/a3_s3_static_evidence.txt.

WHY THE CSS COULD NOT JUST BE MOVED

  In A2 I kept the stylesheet inline in base.html, and said in section 19
  that a file under static/ would load in dev and 404 in prod, because
  runserver serves no static files once DEBUG = False. Tejas confirmed
  that in section 20. Section 3 requires real static files, so the fix
  had to come with it rather than after it.

  WhiteNoise (whitenoise==6.11.0, new in requirements.txt) is now the

35. WHICH FEATURE get_absolute_url() IS USEFUL FOR

Dataset.get_absolute_url() was added by Hriday in models.py:

    def get_absolute_url(self):
        return reverse("data_quality:dataset-detail", kwargs={"pk": self.pk})

The feature it earns its place in is "register a dataset, then go look at
it". DatasetManageView's POST handler creates a Dataset and then has to
send the browser somewhere; without this method the view would have to
know how a dataset's URL is spelled and rebuild it from the primary key:

    return redirect(dataset.get_absolute_url())      # what it does now

The same argument applies to every list that links to a dataset. Four
templates were each rebuilding the same URL by hand:

    <a href="{% url 'data_quality:dataset-detail' dataset.pk %}">   before
    <a href="{{ dataset.get_absolute_url }}">                       after

changed in dataset_list.html, dataset_overview.html, contract_search.html
and dataset_manage.html. The point is not that it is shorter. It is that
"where does a dataset live?" is now answered in exactly one place. If the
route ever becomes /datasets/<slug>/, one method changes and every link
in the project follows; before, five call sites would have had to be
found and fixed by hand, and any that were missed would 404 silently.

36. SECTION 4 (DATA VISUALIZATION - MATPLOTLIB)

  Aggregation + drawing: data_quality/charts.py
  Page view:  data_quality.views.quality_history
  Page URL:   /quality/  (name: data_quality:quality-history)
  Image view: data_quality.views.run_outcomes_chart
  Image URL:  /quality/run-outcomes.png  (name: data_quality:run-outcomes-chart)
  Template:   data_quality/templates/data_quality/quality_history.html

What it shows: how many validation runs ended PASSED, FAILED or ERROR.
On the current demo data that is 4 / 7 / 1 out of 12 runs.

Why this chart and not another one: DataPact's whole claim is "know when
your data breaks". Run outcomes are the headline answer to that. It was
also the only candidate where every category actually has records - a
chart of violations by rule type would have had two permanently empty
bars on this data (NOT_NULL and UNIQUE rules have never failed), and
there is no severity field on Violation to chart at all.

The ORM query:

    ValidationRun.objects.values("status").annotate(total=Count("id"))

Grain: one ValidationRun is one file checked against one contract
version, so a dataset contributes one row per file it has submitted. The
count is of runs, not of failed rows - failed_row_count lives on
Violation, which is a different grain, and mixing the two would produce a
number that means nothing.

Runs against retired contract versions are included on purpose. What
happened in September does not stop being history because the contract it
was judged against has since been superseded.

Two things the query deliberately does not leave to the database. A
status with no runs is filled in as 0 rather than dropped, so the chart
keeps a fixed set of bars instead of silently losing one; and the order
comes from ValidationRun.Status.choices, not from whatever order rows
come back in, so the x-axis does not reshuffle itself between page loads.

Memory and the image endpoint:
  - matplotlib.use("Agg") pins the backend. Agg draws into memory with no
    window system; without it, matplotlib on a machine with no display
    can fail outright.
  - The figure is written to an io.BytesIO buffer and returned as
    HttpResponse(..., content_type="image/png"). Nothing is written to
    disk: the picture is derived from the database and changes whenever a
    run is recorded, so caching it as a file would mean owning cache
    invalidation for something that takes milliseconds to draw.
  - Drawing uses Figure + FigureCanvasAgg directly rather than pyplot.
    This was changed after code review. pyplot keeps one process-wide
    registry of every figure it creates, and Django answers requests on
    threads - runserver does by default, and so does any real WSGI server
    - so two people opening the chart at once would be mutating that
    shared registry from two threads. A Figure built directly owns no
    global state: it is an ordinary object, garbage-collected when the
    request ends, so there is nothing to race on and nothing to leak.
    Two tests cover it: one hits the endpoint repeatedly and asserts the
    number of live Figure objects does not grow, the other asserts the
    pyplot registry stays empty. Both fail if the code is changed back to
    plt.subplots(). This is the kind of bug that never shows up until the
    page has been hit a few thousand times.

Empty database: the endpoint still returns a valid PNG rather than a 500
or a broken image. The bars are drawn at zero and the image says "No
validation runs recorded yet" on its face, because an all-zero chart with
no explanation looks like something failed to load.

Accessibility: the <img> alt text is generated from the same numbers the
chart is drawn from ("Passed: 4 runs. Failed: 7 runs. Error: 1 run."),
and the page repeats the figures in a plain table underneath. An image on
its own would put the numbers out of reach of a screen reader, and out of
reach of anyone whose connection drops the image.

34. THE CHARTS NAV LINK - WHY IT IS NOT WRITTEN THE WAY IT WAS ASKED FOR

Tejas asked for this in base.html's nav:

    <a href="{% url 'data_quality:charts' %}"
       class="{% if request.resolver_match.url_name == 'charts' %}is-active{% endif %}">Charts</a>

There is no route named "charts" on main. urls.py has home, dataset-*,
contract-search, dataset-manage, quality-history, run-outcomes-chart,
dataset-api, reports and the two export routes. "charts" is a Python
module (data_quality/charts.py, Tejas's matplotlib helper), not a URL
name, which is probably where the name came from.

{% url %} raises NoReverseMatch when the name does not resolve, and
base.html is inherited by all eight page templates. So that one line
does not produce a dead link - it takes the whole site down. Measured,
not guessed:

    python manage.py test data_quality   ->  FAILED (errors=68) of 111
    /            500        /contracts/search/   500
    /datasets/   500        /reports/            500
    /datasets/1/ 500        /quality/            500

Every page, both settings modules. In deployment week.

What is committed instead:

    {% url 'data_quality:charts' as charts_url %}
    {% if charts_url %}
