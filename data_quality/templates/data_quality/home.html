{# ------------------------------------------------------------- problem #}

Files change. Reports break quietly.

A recurring export looks the same every month, until it doesn't: a new status code, a negative total, a reading off the scale. Without a written expectation, nobody can say whether the file is wrong or the expectation is out of date.

{# -------------------------------------------------------- how it works #}

Four steps, one record of every decision.

  1. Register the dataset

    Name the file that arrives again and again, such as a monthly enrollment export, with its owner and the office that sends it.

    {% if user.is_authenticated %}
    • Browse datasets
    • Register a dataset
    {% endif %}

  2. Write its contract

    List what every delivery must satisfy: types, ranges, allowed values, formats, no blanks, no duplicates. Each change becomes a new version with a note saying why.

    {% if user.is_authenticated %}
    • Search contracts
    • See which version is active
    {% endif %}

  3. Record each run

    Each check of a delivered file is kept as a validation run. Every rule it broke becomes a violation, with the number of failed rows and a few sample values.

    {% if user.is_authenticated %}
    • Look up violations
    {% endif %}

  4. Decide the cause

    A person records whether each violation was a data issue or a contract that needed updating. An AI model can suggest which, first.

{# ---------------------------------------------------------- AI section #}

The AI suggests. A person decides.

From the record

Dataset
Monthly Enrollment Export, contract v3
Run
enrollment_2026_09.csv, 1 September 2026
Rule
status ALLOWED_VALUES ["ACTIVE", "INACTIVE"]
Rows failed
4 of 4,812

AI suggestion Illustrative answer, in the format DataPact accepts

Explanation
Four rows carry AUDIT, a status the contract does not list. The value is consistent and well formed, which points to a new enrolment category rather than a typing error.
Likely cause
The contract needs updating
Next step
Confirm AUDIT with the Registrar and add it to the allowed values.

The decision

A person records it: Contract updated A suggestion never changes a record or resolves a violation by itself.

Model in production
openai/gpt-oss-20b, through the Groq API.
What leaves the server
The dataset, column, rule and row counts. Sample values only when they are known status codes such as AUDIT, at most three. Names, numbers, emails and IDs from the file are never sent.
Checked before you see it
The reply must be three non-empty fields with one of the two allowed causes. Anything else is discarded, and the page says no reliable explanation came back.
Local models
SmolLM2-1.7B-Instruct and the handbook search run on a team machine for development. The public host cannot hold them, so they are switched off there.
Measured
Every request's latency, tokens, cost and outcome go to the AI analytics dashboard, with benchmark runs kept apart from real use.

{# --------------------------------------------------------------- today #}

What works today, and what doesn't yet.

Live on this site

  • Dataset registry, search and registration
  • Versioned contracts with a note for every change
  • Recorded validation runs and violations, with their resolutions
  • AI explanations through the Groq API
  • AI analytics: latency, cost and outcomes
  • CSV and JSON exports, and a public run-outcomes API
  • Sign-in with a username or a Google account

On a local machine only

  • Explanations from SmolLM2-1.7B-Instruct
  • Handbook questions answered from retrieved passages (MiniLM embeddings)

Both need more memory and disk than the public host offers.

Planned

  • Uploading a delivered file
  • Checking it against its contract automatically
  • Editing contract rules in the browser
